# Preview Contract

## Overview

Rules for surfaces — the runnable HTML/CSS/JS previews under `components/` and `pages/` — their `.spec.yml` files, the markers that tie spec to code, and the viewer. Surfaces are plain HTML, CSS, and JS: no framework, no build step, community libraries from a CDN allowed.

## Guidelines

### Surfaces

| Kind | Folder | Owns | Refers to |
| --- | --- | --- | --- |
| Component | `components/` | Variants, its own states, its own motion (hover, enter, exit) | Tokens, primitives |
| Page | `pages/` | Page states, page choreography (reveal order, scroll-driven changes, section transitions), content | Components by name |

A page never restates a component's variants, states, or motion. It shows the component in the page state that uses it (`submit-error` → `toast` `error`).

### Files per surface

| File | Holds |
| --- | --- |
| `<name>.html` | Markup. Links `../system/tokens.css`, `../system/type.css`, `../system/motion.css`, used component CSS, then its own CSS; scripts `../system/preview.js`, `../system/motion.js`, used component JS, then its own JS |
| `<name>.css` | Rules for this surface only; values via tokens (`var(--color-primary)`), no raw values where a token exists |
| `<name>.js` | Behavior and state handlers; omit when there is none |
| `<name>.spec.yml` | States, variants, motion, content — see **Spec file** |

Kebab-case names. Light-first; render dark mode only when `design.md` defines it. Anything two surfaces share lives in `system/` or `components/`, never copied between surfaces. A component page is a gallery: every variant shown at once, live.

Templates: [`../assets/surface/`](../assets/surface/).

### States

States are end views — what the surface looks like after something happened (validation error, empty list, modal open, mobile menu open). Interaction states (hover, focus, pressed) stay live in CSS and are not listed.

Each non-default state is entered by the surface's own code:

```js
Preview.state("submit-error", () => showToast("error"));
```

The handler calls the same functions real use would call, so its motion plays when the state is entered. The viewer reloads the surface for each state, so handlers start from a clean page.

A page registers its states in `<name>.js`. A component registers its states in an inline `<script>` at the end of its gallery `.html`; its `.js` holds behavior only, because pages load it too.

### Spec file

```yaml
surface: pages/contact          # folder/name
kind: page                      # page | component
intent: Collect one idea and say what happens next.
uses: [button, field, toast]    # components shown on this surface
viewports: [desktop, tablet, mobile]

variants:                       # component only
  - id: error
    description: Destructive tone; stays until dismissed.

states:
  - id: default
    description: Empty form.
  - id: submit-error
    trigger: server rejects the inquiry
    description: Form keeps its values; toast explains and offers retry.
    shows: toast#error          # component#variant-or-state

motion:
  - id: toast-enter
    target: toast               # value of data-motion
    trigger: state              # see Triggers
    when: toast opens
    description: Rises from the bottom edge; form stays interactive.
    uses: [slide-up, fade]      # primitives from design.md → Motion
    params: { delay: 0ms }      # optional overrides, in tokens where possible
    reduced: fade only

content:
  - slot: contact-title         # value of data-slot
    role: material              # sample | canonical | material
    source: PRD Contact intent  # where the words or facts came from
```

Omit empty lists. `default` is always the first state.

### Markers

Write markers literally in the HTML so they can be found without running code. Elements generated by JS are covered by their static parent's marker.

| Marker | On | Must match |
| --- | --- | --- |
| `data-motion="<id>"` | The element the motion moves, or the parent of a staggered or generated group | A `motion` entry `target` |
| `data-slot="<slot>"` | The element holding a content slot | A `content` entry `slot` |
| `data-component="<name>"` | The root element of a component instance | A `uses` entry |
| `Preview.state("<id>", …)` | The surface's JS | A non-default `states` entry |
| `@motion <name>` | A comment in `system/motion.css` or `system/motion.js` | A primitive in `design.md` → Motion |

### Triggers

| Trigger | Fires when | `when` names |
| --- | --- | --- |
| `load` | Page loads | — |
| `in-view` | Target enters the viewport | Threshold, e.g. `20% visible` |
| `scroll` | Scroll position crosses a point or drives progress | The point or range |
| `hover` | Pointer over target (desktop only) | — |
| `focus` | Keyboard focus reaches target | — |
| `action` | User clicks, taps, submits, or types | The action |
| `state` | A state is entered or left | The state |

### Viewer

`<design-root>/preview.html` lists surfaces from `system/surfaces.js`, loads the chosen one in a frame sized to the chosen viewport, and lists that surface's states. Choosing a state reloads the frame and runs its handler. The selection lives in the URL hash, so a link reopens the same view. It works from `file://` and from any static server.

`system/surfaces.js` entry: `{ id: "pages/contact", label: "Contact", viewports: ["desktop", "tablet", "mobile"] }`.
